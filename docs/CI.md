# Release automation

The release workflow is `.github/workflows/release.yml`.

## Trigger

The workflow runs on:

- every push to `main` or `master`;
- an explicit `workflow_dispatch` run.

It does not run on a schedule.

The workflow never changes `VERSION` and never creates a commit. It reads the
version prepared locally and publishes exactly that version. A release push
therefore does not put the local branch behind the remote.

## Version

`VERSION` is the single source of the full `major.minor.patch` version. The
matching release notes live in `changelogs/<version>.md`.

Prepare a release locally:

```powershell
pwsh ./scripts/version.ps1 -Bump patch
pwsh ./scripts/version.ps1 -Bump minor
pwsh ./scripts/version.ps1 -Bump major
```

The command writes `VERSION` and prints the new value. It creates
`changelogs/<version>.md` with a placeholder if the file does not exist. Replace
the placeholder with the actual release notes, then commit both files.

Each version has its own changelog file. `CHANGELOG.md` is only a link index; the
workflow does not parse or concatenate it.

`scripts/version.ps1` refuses to move to an equal or lower version. It also
supports an explicit value for controlled use:

```powershell
pwsh ./scripts/version.ps1 -Set 1.0.0
```

Example release preparation:

```powershell
pwsh ./scripts/version.ps1 -Bump minor
# edit changelogs/<printed-version>.md
git add VERSION changelogs/<printed-version>.md
git commit -m "Release <printed-version>"
git push origin main
```

The workflow passes the resolved version to MSBuild through `PkgForgeVersion`;
the AOT binary reports exactly that value.

## Pipeline

1. Verify that `VERSION` is `major.minor.patch`.
2. Verify that `changelogs/<version>.md` exists and has no placeholder text.
3. Refuse the run if `v<version>` already exists on the remote.
4. Cache and restore NuGet packages.
5. Verify formatting with `dotnet format --verify-no-changes`.
6. Run the complete regression suite with the release version.
7. Build the Windows x64 NativeAOT archive with `release.ps1 -NoSource`.
8. Run the regression suite again against the packaged AOT executable.
9. Upload three files as a workflow artifact:
   - `pkgforge-<version>-win-x64.zip`
   - `release-manifest.json`
   - `SHA256SUMS.txt`
10. Only after the build job succeeds, replace the GitHub release:
    - delete all existing releases;
    - delete remaining `v*` tags;
    - create `v<version>` at the current commit;
    - upload the three assets.

Because metadata is checked before the build and the tag must not already
exist, a forgotten version bump fails early. A repeated version cannot silently
replace an already-published one.

The release body is generated by reading `changelogs/<version>.md` directly and
adding a short asset summary.

## Release assets

The release contains the Windows x64 binary archive, release manifest, and SHA-256
checksum file. Source code is not uploaded as a release asset. The tagged commit
and GitHub's automatically generated source archives are the source delivery.

## Permissions

The workflow uses the automatic `GITHUB_TOKEN` when `RELEASE_TOKEN` is absent,
and requests:

```yaml
permissions:
  contents: write
```

That permission covers release creation/deletion, tag deletion, and asset
upload. It is not used to push source commits.

The repository must allow GitHub Actions to obtain a write token:

```text
Settings -> Actions -> General -> Workflow permissions
  Read and write permissions
```

If an organization policy pins the token to read-only, use a fine-grained PAT.
For a repository-scoped fine-grained token:

| Permission | Access | Why |
| --- | --- | --- |
| Contents | Read and write | Releases, tags, assets |
| Metadata | Read | Mandatory repository metadata |
| Actions | Read | Optional, only for workflow-run diagnostics |

No Administration, Workflows, Packages, Environments, or organization
permissions are needed. For a classic PAT, the `repo` scope is sufficient for a
private repository; `public_repo` is the reduced public-repository equivalent.

The workflow supports an optional `RELEASE_TOKEN` secret. It is used for
checkout and `gh` when present, and ignored otherwise, so adding a PAT later
requires no workflow edit.

Tag protection rules can prevent automated deletion or creation of `v*` tags.
If tag protection is enabled, grant the token the required repository
permission or remove the protection for the release tag pattern.

## Toolchain pinning

The workflow pins the major line of every moving build dependency:

| Component | Pin |
| --- | --- |
| Build runner | `windows-2025` |
| Publish runner | `ubuntu-24.04` |
| Checkout action | `actions/checkout@v7` |
| .NET action | `actions/setup-dotnet@v6` |
| Upload action | `actions/upload-artifact@v7` |
| Download action | `actions/download-artifact@v8` |
| .NET SDK | `10.0.x` plus `global.json` |

These are major-version pins. The action repositories may publish compatible
minor and patch releases within those major tags, but a new major version is a
deliberate update. The operating-system runner labels are fixed images rather
than `windows-latest` or `ubuntu-latest`, so an image migration does not change
the build environment without a workflow change.

The actions listed above run on Node.js 24. No separate Node.js setup is used;
the runtime comes from the action major version.

The .NET SDK major is 10. `global.json` sets `10.0.100` with
`rollForward: latestFeature`, so the installed 10.0 feature band and patch are
selected by the SDK while the major stays fixed.

If a build dependency needs a major upgrade, update it together with a full
release validation. Do not silently float a major version.

## AOT

The current build job uses `windows-2025`; the publish job uses `ubuntu-24.04`.
NativeAOT is platform-specific and must run on the target platform. Windows x64
is the only release target currently configured. Linux and macOS would require
matching runners and platform-specific packaging; they are not cross-compiled
from Windows.

If NativeAOT is unavailable on the runner, the build fails before any release
is changed. A framework-dependent fallback would require changing `release.ps1`
and the asset layout; it is not silently substituted.

## Failure behavior

Metadata validation, formatting, regression, and packaged-AOT checks all run
before the publish job. A failure before or during those checks leaves the
current release and tags untouched.

The publish job is the only destructive stage. It replaces release history
intentionally, so a failure after deletion can leave the release page empty.
A later push waits for an in-flight release run rather than cancelling it.

## Local equivalent

The local release command reads `VERSION` when `-Version` is omitted:

```powershell
pwsh ./scripts/release.ps1
```

The workflow uses:

```powershell
pwsh ./scripts/release.ps1 -Version <version> -NoSource
```

`-NoSource` produces only the binary archive, root release manifest, and root
SHA-256 file, matching the workflow assets.
